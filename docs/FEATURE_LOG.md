## 一、视频转文字稿（ASR）

## 二、高光候选生成（召回）

这是整个产品变化最剧烈的功能，经历了三次策略转向：

**v0.2（2026-09-08）** 整篇直喂
- 把整场文字稿一次性交给 AI，让它直接挑高光
- 问题：长文本只看前半段就下结论，**前半段偏置**——后面的爆点永远轮不到

**v0.3 Phase 1（2026-09-09）** 全覆盖扫描
- 改为本地信号扫描：每一分钟打一个「热度分」，哪里词密集、哪里有强信号词（卧槽/炸了/笑死等）哪里热
- 热的地方切成小区块细看，冷的地方切成大区块粗看，保证**时间轴 100% 覆盖，一个区块都不漏**
- 实测：51 分钟直播 14 个区块，热区集中在 29-35 和 47-51 分钟——前半段偏置**结构性解决**

**v0.3.1（2026-09-09）** 召回优先
- 背景：真实测试 AI 输出 0 个高光，人工复盘发现该场明明有多个明显爆点——问题不是覆盖不足，是**第一轮就把候选掐死了**
- 改为「宁多勿少」：每个区块至少 1 个候选、拿不准就先收进来、第一轮不判生死
- 新增三类高光分类：**事件型**（有完整故事）/ **情绪型**（主播爆发）/ **梗型**（一句话成名）
- 实测：候选池从 1 个涨到 36 个，上一版漏掉的爆点全部召回

**v0.3.2（2026-09-09）** 发现视角换脑子
- 海选提示词同步升级：每个候选先自问「**一个不认识主播的新用户刷到开头 3 秒，为什么会停下来？**」——找的是钩子（误会/悬念/强反差/离谱事件），不是「这段讲了啥」
- 新增「假高光」警惕清单：普通失误、普通展示、单纯惊讶、普通评价——表面热闹，通常不是真爆点（海选仍不判生死，只是别把它们当首选，过滤权留给复审）

## 二·五、事件聚合（v0.4 新增）

**从什么样 → 变成什么样**：v0.3 的高光基本单位是「一句话/几秒」，一个完整事件（拆包装→份量少→试吃→吐槽像纸盒）会被拆成 5 个各自低价值的候选，AI 逐个评价，结果全判成「普通」。v0.4 增加事件聚合层，把候选先还原成「完整事件」再交给复审——**AI 从评价一句话，升级为评价一件事**。

**怎么做（分三层，本地只提分组、AI 才做判断）**：
1. **本地粗聚类**（`event_cluster.build_clusters`）：给候选两两打「关联分」（时间距离 + 时间重叠 + 主题相似 + 相邻加分），够线就连边、连通分量成簇。铁律：**孤立候选自成一簇绝不删**，没有任何「超过 X 秒就断开」的硬规则——一个持续 10 分钟的事件只要中间候选连续就能一路串起来
2. **AI 事件判断**（`build_event_judge_prompt`）：针对每簇问「这是不是同一件事」，输出事件边界/摘要/结构（铺垫/发展/结果）/最强爆点；故事不完整就回 `need_more_context`，系统自动扩大上下文重判（先 ±90 秒，不够扩到 ±240 秒）
3. **事件级去重**（`_dedupe_events`）：时间重叠 >50% 且主题相同才合并——宁可漏合并留重复，也不误合并把两件事并成一件

**实测效果**（51 分钟真实稿，标准模式 ¥0.3078）：
- **19 个候选 → 16 个事件**（AI 合并 3 次、拆分 2 次、上下文扩大 2 次、判断 0 次失败）
- 关键爆点「2014 罐头发现异物仍要吃」从 2 个碎片正确聚合为 **2.6 分钟完整事件**（B 级 7.8 分，全场最高），结构完整（铺垫=挑出过期罐头 / 发展=开罐发现异物 / 结果=狂言要吃）
- 动态时长生效：高光从 **11 秒**（一句话自嘲）到 **162 秒**（完整事件），不再固定 20/30 秒
- 同时修掉 3 个潜伏 bug：复审提示词缺 event_id、五维子分键名不一致（真实 API 下全会回落 5 分）、事件拆分时共用边界导致去重误合并（详见 D-034/D-035）

## 三、高光复审与淘汰

**v0.3 Phase 2（2026-09-09）** 严格淘汰制
- 第二轮 AI 以「资深直播短视频运营」身份复审每个候选，不合格直接毙掉并给出拒绝理由
- 首次真实测试：唯一候选被毙，全场 0 推荐——淘汰机制是真在干活，但**过严**

**v0.3.1（2026-09-09）** 分级替代生死
- 复审从「推荐/毙掉」二元制改为 **A/B/C/D 四级**：A 强烈推荐剪 / B 值得测试 / C 备用素材 / D 淘汰
- 新增**零输出禁令**：除非全场候选都低于 4 分且无任何情绪节点和独立成片可能，否则不允许输出 0 个；代码层还有兜底（全灭时最佳候选 ≥4 分强制保留一个 C 级）
- 实测：36 候选 → 7 个 A 级 / 19 个 B 级 / 10 个 C 级，0 淘汰

**v0.3.2（2026-09-09）** 五级分级 + 负面清单封顶
- A/B/C/D → **S/A/B/C/D 五级**：S 爆款候选（≥9.0）/ A 强推荐（≥8.0）/ B 测试素材（≥6.0）/ C 备用素材（≥5.0）/ D 淘汰
- 新增「不值得剪」**负面清单**（普通失误 / 普通展示 / 单纯惊讶 / 依赖上下文 / 普通评价）：复审命中任一就填 negative_flags，**本地强制封顶 B 级**——AI 说破天也进不了 S/A，「事故 = 高光」被结构性杜绝（只降不升，本来就是 C/D 的不动）
- 每个候选复审必答两句：**为什么值得剪**（陌生人为何停留 + 核心传播点，写不出来 = 可能不值得剪）+ **最大风险**（必须诚实指出短板，禁止写「无」）
- 复审不再给总分和等级，只打五个子分「零件」，等级由本地组装——AI 不能靠一句漂亮理由把普通失误捧上精品位

**v0.4 步骤 3（2026-09-09）** 分批复审 + 全局排序（D-037）
- 事件聚合后单事件原文变长，「一次审完所有事件」会单次 prompt 过大、后面的事件被忽略、前半段事件占便宜（前半段偏置）——**改成分批**：每批 ≤3 事件独立复审，结果按 event_id 对号入座（禁依赖返回顺序），AI 报「上下文不够」就单独扩窗重审一次
- 复审完 **Global Ranking** 全量按最终分降序排（跨 batch 统一，消除前半段偏置）；各 batch 用同一评分标准，无批次优劣
- 整场 AI 复盘报告从复审里拆出来独立一次调用（REPORT_SYSTEM，基于事件精华卡），分批复审的每个 batch 不再背负整场报告

**v0.4 步骤 3（2026-09-09）** schema 校验 + 动态剪辑时长（D-038/D-039）
- 复审输出改为协议 JSON：event_id / scores / recommended_start/end/duration / duration_reason / why_cut / risk / context_incomplete；缺字段一律记 warning + 明确 fallback，绝不静默用 5 分掩盖
- 动态时长：recommended_start/end/duration + duration_reason，不固定 20/30/60s（一句话梗 8s、完整反转几十秒、连续事件几分钟）；Context Window 与 Clip Duration 完全分离
- recommended 时间格式统一 mm:ss（AI 会混回 HH:MM:SS）+ 偏离事件边界 >120s 自动兜底

## 五、评分标准

**v0.3 Phase 2** 初版权重
- 传播 30 / 情绪 25 / 冲突反转 20 / 独立观看 15 / 内容 10（2026-09-09 规范 v1.0 定稿，D-012）

**v0.3.1** 权重 v2（D-020）
- 传播 30 / 情绪 25 / **主播个人特色 15** / **争议讨论 15** / 独立成片 10 / 内容 5
- 变化逻辑：直播不是纪录片，很多爆款来自人物反应而不是完整故事

**v0.3.2（2026-09-09）** 评分模型 v3（D-022）——从「内容好不好」转向「能不能火」
- 背景：人工复盘发现 AI 打分还是在评价「这件事大不大、主播惊不惊讶」——饮料粉洒出来、军粮份量少这种事故被评高分；而部分 B 级候选（误会/反差/有记忆点）反而更适合剪。问题根源：**评分维度里没有「三秒吸引力」和「反差」，全是内容维度**
- 变成什么样：
  - 五维全换：**三秒吸引力 30 / 反差意外 25 / 人物表现力 20 / 独立成片 15 / 事件完整度 10**（删除情绪冲击/争议讨论这类「热闹度」维度——惊讶不等于高光）
  - 复审 AI 只打五个子分（1-10），总分本地按权重加权、等级本地按分数线定：分数来源全程可审计，AI 也没有「先给漂亮理由、再顺手打 9 分」的空间
  - 案例校准写进提示词：黄腐鸡误当咖啡（误会+反差）该高分；军粮「像纸盒子」、罐头「像指甲盖」（具体比喻 = 天然标题/记忆点）该高分；饮料粉洒出来、「哇好少」（纯事故/纯惊讶）不给高分
  - 每个候选带「五维判决书」：三秒吸引力 8 分 / 反差意外 9 分……剪之前先看它到底赢在哪、输在哪

**v0.4 步骤 3（2026-09-09）** 100 分制 + 四档对外（D-036）
- 背景：1-10 分太粗、区分度不足，用户反馈 ABC/S 表达不了剪辑价值
- 变成什么样：
  - 复审 AI **仍只打五维子分（1-10）**，本地按权重加权后 **×10 得 0-100 总分**（可解释可审计）
  - 对外四档：**S≥90 必剪 / A≥80 强烈推荐 / B≥60 值得测试 / C≥50 备用/不推荐**；D<50 仅内部淘汰标记，不再对外展示（C 即最低对外档）
  - 阈值 = 原 1-10 制 ×10，语义同构，step1/step2 测试不回退
  - UI 徽章：S 必剪 / A 强烈推荐 / B 值得测试 / C 备用·不推荐（GRADE_UI）

## 七、用户专属词库

**v0.3 Phase 1（2026-09-09）** 已建立，待填充
- `user_lexicon.txt` 一行一个词：主播口头禅、专属梗、直播间黑话
- 写进去的词被当成强信号，出现就给那一分钟加热度
- 当前作用是**调扫描深度**；「根据词库纠正识别错字」是下一阶段（P1）功能

**v0.4 第一步（2026-09-09）** ASR 纠错词库上线（与 user_lexicon.txt 是两套东西）
- **从什么样 → 变成什么样**：以前只有「调扫描深度」的词库（出现就给那一分钟加热度），识别错字完全没人管——主播名、游戏名、品牌、热词被 Whisper 写成同音字，文字稿是脏的，AI 判断的上限被压住。现在新增 `custom_dictionary.json`：识别完之后按「错词 → 正确词」对照表替换，**输入先弄干净再交给 AI**
- **为什么这么做**：用户要求 v0.4「先做基础版本，暂不做复杂 AI 纠错」。纯字符串替换零成本、零延迟、结果完全可预测，改了什么一眼能看到；真正难的上下文感知纠错（判断「福岛」到底是地名还是伏特加）留给 v0.5
- **怎么用**：按分类填（主播名字 / 游戏名称 / 品牌 / 网络热词 / 其他），改完保存。生效时机是**识别完、存稿前**——`transcripts/` 里的稿子一开始就是干净的；历史稿可以用 `pipeline.correct_existing_transcript` 单独补一遍
- **效果**：实测「福岛→伏特加」「和平经营→和平精英」替换成功；时间戳一个字不动（已写成自测验收项，防止整篇替换毁掉时间轴）
- **细节**：长词优先替换（否则「伏特加酒」会被「伏特加」先咬一半）；词库文件缺失或写坏 → 当作不纠错，绝不带崩分析

## 十一、反馈闭环

**v0.3.1（2026-09-09）** 基础就绪，UI 未接
- 每个候选有唯一编号（clip_id），未来 👍/👎 按钮的数据就挂在这个编号上
- 设计原则：只攒数据，先不急着用反馈改提示词（那是 v0.4 的事）

**v0.4 第一步（2026-09-09）** 从「只有编号」到「真的能记账」
- **从什么样 → 变成什么样**：v0.3.1 只发了个 clip_id，用户点了赞也没有地方存——反馈闭环是断的。现在新增 `analysis/feedback.py` + 本地 `feedback.json`：用户的「喜欢 / 不喜欢 + 原因」真的会被写下来，而且是**和片段当时的样子一起存**（snapshot：标题/时间/分数/等级）
- **为什么这么做**：用户 v0.4 需求原话——「目的：未来 v0.5/v1.0 训练自己的判断体系。现在不上传服务器。」也就是说这一步的唯一任务是**把素材攒够、攒对**。只记态度和原因是不够的，将来要回答「用户喜欢的片段有什么共同点」，必须有片段本身的特征，所以顺手把 snapshot 一起存
- **怎么运作**：
  - 文件是 JSON 数组（不是 jsonl——用户给的格式就是单个对象，数组最直观，任何 JSON 解析器都能直接读）
  - 同一个 clip_id 再反馈 → **覆盖**（用户改主意了，以最新判断为准），不堆积重复数据
  - 覆盖时**继承旧的 snapshot**：片段的客观信息不随用户态度改变，不继承的话将来分析会缺数据（这是自测里抓出来的真问题，已修）
  - 文件被改坏 → 自动备份成 feedback.corrupt.json 重新开始记，不能因为文件坏了就丢掉整个反馈能力
- **现在不做**：不上传服务器、不做分析、不拿反馈改提示词——按用户要求全部留给 v0.5/v1.0
- **UI 按钮**：界面上的 👍/👎 还没接（留在 v0.4 步骤 4 一起做），模块和文件格式已经先就位
