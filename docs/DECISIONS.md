## D-001 为什么不用一次性把全文丢给 AI 分析？

**背景**：v0.2 就是这么做的（截断 6000 字 + 单次调用），结果：
- 长直播后半段直接丢失（截断）
- LLM 存在前半段注意力偏置，后面的内容容易被遗漏
- AI 的任务是「找重要内容」，不是「找值得剪的内容」

**决策**：采用多阶段流水线——分段分析 + 候选池 + AI 复审。
每段独立分析消灭位置偏置；复审层用运营视角淘汰，对齐「值得剪」的目标。

## D-002 候选信号扫描层为什么绝不过滤？

**原因**：直播高光可能来自突然事件、故事反转、情绪变化、甚至平静但有价值的观点。
词库只能测「热闹度」，测不了「价值」。
如果扫描层有权跳过区域，就会漏杀「平静但值钱」的片段。

**决策**：扫描层只调分析深度（热区细切 / 普通区粗切），所有时间段必须进入 AI 分析流程。
这条铁律写在 event_scanner.py 和 chunker.py 的文件头注释里，谁改谁负责。

## D-003 AI 的身份为什么是「运营」而不是「总结助手」？

**背景**：用户指出 v0.2 的 AI 像观众（「这个挺有意思」），但产品需要 AI 像运营（「这个发出去有人看吗」）。

**决策**：所有 v0.3 提示词的 system 身份统一为「拥有多年经验的直播短视频运营人员，任务不是总结直播内容，而是判断哪些片段值得剪辑发布」。海选必须回答三问：为什么用户会停留 / 为什么适合短视频 / 为什么不是普通聊天。

## D-004 为什么要有复审淘汰机制？

**背景**：海选容易放宽标准（AI 找候选时倾向于多给）。例：主播安慰粉丝——情绪价值高，但缺冲突、缺讨论点、外人没有观看动力、需要大量上下文，发出去没人看。

**决策**：复审层带淘汰权（recommend false + reject_reason[]），让 AI 学会拒绝「垃圾高光」。
判断口诀：**情绪价值 ≠ 传播价值**。同时复审要产出分析报告，向用户解释「为什么没推荐更多」——不解释，用户会以为 AI 没认真分析。

## D-005 为什么 Token 三模式不直接展示 token 数字？

**原因**：用户（最终使用者）关心的是效果、速度、价格，不是 token。暴露数字只会制造理解负担。

**决策**：UI 只显示模式名（快速/标准/精细）+ 预计时间/成本/精度描述。预算数字留在 config.py（TOKEN_MODES）。

## D-006 为什么数量模式叫「候选池」而不叫「全部」？

**原因**：「全部」暗示不加筛选地倾倒结果，用户会被垃圾候选淹没。

**决策**：候选池模式展示所有超过最低质量线（score ≥ 6，config.MIN_QUALITY_SCORE）的候选，且每个都带 AI 的 recommend 标记，用户自己权衡。

## D-007 为什么词库分三层（通用强词 / 类型词库 / 用户词库）？

- 通用强词：情绪爆发是所有直播类型的万能信号（含 ASR 错字变体：卧槽/卧草/我操）
- 类型词库：不同直播的爆点语言完全不同（吃瓜 vs 五杀 vs 反常识）
- 用户词库：主播黑话、圈内梗，系统不可能预知 → 用户自己加（一行一词，按强信号算）
- AI 自动发现词库 → 推迟 v0.4（先验证核心判断能力，见 D-008）

## D-008 为什么把词库自动发现 / 文本纠错 / 反馈分析推迟到 v0.4？

**原因**：v0.3 的核心目标是验证「AI 能不能像真正的直播剪辑师一样判断片段值不值得剪」。
核心没验证之前堆外围功能 = 在没打地基的地上盖楼。

**决策**：v0.3 只做核心流水线 + 攒数据（feedback.jsonl 只写不分析），v0.4 再回头做外围。

## D-009 API Key 为什么走环境变量 / api_key.txt，不写进代码？

安全常识 + 仓库是（虽然是私有）GitHub 仓库。env 优先，api_key.txt 兜底（网页版用），两者都已在 .gitignore 排除。

用户明确要求（2026-09-08）：初学者项目，Streamlit 纯 Python 可维护，不引入前端工程链。

## D-012 高光评分的五维标准（规范 v1.0，2026-09-09）

**决策**：高光判断的长期评分标准为五维加权：

| 维度 | 权重 | 含义 |
|---|---|---|
| 传播价值 | 30% | 陌生用户刷到，会不会停下来 |
| 情绪冲击 | 25% | 愤怒/惊讶/兴奋/搞笑/感动 |
| 冲突反转 | 20% | 观点冲突/意外结果/争议 |
| 独立观看价值 | 15% | 脱离直播上下文是否成立 |
| 内容价值 | 10% | 知识、信息价值 |

各直播类型在此基础上调整侧重（游戏：操作/胜负/反转；娱乐：情绪/冲突/梗；知识：信息密度/认知冲击）。
**落位**：写入海选/复审提示词的时机 = 下一次触碰 prompt_builder 时（P0 真实测试调优阶段），不在文档变更时提前改代码。

## D-013 云端部署架构：本地 ASR + 云端 AI 分析（规范 v1.0，2026-09-09）

**原因**：商业化后不能让用户上传视频——带宽与存储成本高。
**决策**：视频读取、ASR 全部在用户本地完成；云端只处理 AI 分析（文字稿上行，结果下行）。
同时降低用户电脑配置要求（P3）。v0.5 落地。

## D-014 文本纠错优先级由 v0.4 提前到 P1（规范 v1.0，2026-09-09）

**背景**：D-008 曾把文本纠错整体推迟到 v0.4（先验证核心判断能力）。
**修订**：规范 v1.0 将文本纠错第一阶段（用户词库管理 UI：添加/删除/修改/导入/导出）提为 P1，理由：**输入质量决定 AI 判断上限**——Whisper 的人名/游戏名/品牌错字会直接污染海选证据。
**注意**：这不是推翻 D-008——P0 仍是真实 AI 测试（核心验证依然最优先），只是纠错紧随其后；AI 辅助发现词库（第二阶段）仍推迟。
**落位**：新建 analysis/correction.py，禁止大规模重构现有模块。

## D-015 Token 展示规范修订：模式选择不露数字，运行前必须给预估（规范 v1.0，2026-09-09）

**背景**：D-005 规定 UI 不展示 token 数字。
**修订**：两者不冲突，规范更精确——
- 模式选择界面：只显示 快速/标准/精细 三个名字，不露参数（D-005 不变）
- **运行前**：必须显示预计消耗（如「预计 Token：约 18000，预计费用：¥0.08」）——budget.py 已具备估算能力，Phase 3 UI 接入
- 最大 token 限制用户可修改，默认 50000（config）

## D-017 召回优先：海选「宁多勿少」取代「宁缺毋滥」（v0.3.1，2026-09-09）

**背景**：P0 真实 API 首测（51 分钟稿）最终 0 推荐、1 个被拒候选。人工复盘发现该直播实际存在多个明显适合切片的爆点——问题不是覆盖不足，而是**候选生成阶段漏掉大量潜在高光 + 复审过滤过严**。海选提示词里的「宁缺毋滥」让 AI 倾向于「不够完美就不要」。

**决策**：策略从「严格筛选」调整为「**先保证召回率，再保证精准率**」：
- 海选：每区块至少 1 个候选（最多 3 个），拿不准就给，让复审去淘汰——第一轮不判生死
- 51 分钟直播目标候选池 15~30 个
- 「宁可多给候选，不要提前杀死可能爆的视频片段」写进海选 system 身份

**与 D-004 的关系**：不是推翻——复审仍有淘汰权（D-004 不变），只是淘汰权只保留给复审层，海选层不再提前用。

## D-018 复审从二元 recommend 改为 A/B/C 分级 + 零输出禁令（v0.3.1，2026-09-09）

**背景**：二元 recommend（推荐/拒绝）容易让 AI 一刀切输出 0 个。直播不是纪录片，很多爆款来自人物反应而非完整故事，硬套「完美才推荐」会误杀。

**决策**：
- 复审输出等级：**A 级**（≥8 强烈推荐）/ **B 级**（6~7 建议测试剪辑）/ **C 级**（5 备用素材）/ D（<5 淘汰 + reject_reason）
- **零输出禁令**：不允许把所有候选都打 4 分以下，除非同时满足：全部传播价值极低 + 无明显情绪节点 + 无独立成片可能
- 代码兜底（`_enforce_no_zero`）：复审全灭时，只要最佳候选 ≥4 分，强制保留 1 个为 C 级（标 `forced_keep`），请用户人工复核
- 数量模式重定义：自动精选 = 只出 A 级；候选池 = A+B+C 全展示；自定义数量 = 前 N 个分层标注（高质量/普通/备用）

## D-019 新增漏检质检层（质检 AI）（v0.3.1，2026-09-09）

**决策**：海选后、复审前插入一个独立角色「质检 AI」：
- 输入 = 各区块本地摘要（热/普、信号分、已有候选数、含强信号词的关键句，零 API 成本生成）+ 候选池简表
- 任务不是找高光，而是回答「有没有区块明显存在爆点却没进候选池」
- 查出可疑区块 → 用更宽的标准重扫该区块（second_pass 提示词），新候选去重后并入候选池
- 保险丝：最多重扫 `MISS_CHECK_MAX_CHUNKS=3` 个区块（防成本失控）；质检坏回复不崩（当无漏检处理）

## D-020 评分权重 v2：加入主播特色与争议讨论（v0.3.1，2026-09-09，修订 D-012）

**背景**：D-012 五维标准（传播 30/情绪 25/冲突反转 20/独立观看 15/内容 10）偏向「专业短视频运营」视角。实测教训：直播的高光逻辑不同——**很多爆款来自人物反应，而不是完整故事**。

**决策**（v2 权重，已写入海选提示词）：
- 传播潜力 30% / 情绪冲击 25% / **主播个人特色 15%** / **争议讨论 15%** / 独立成片 10% / 内容价值 5%
- 同时引入三类高光类型，各有专属评分维度：**事件型**（故事完整/冲突/信息价值）、**情绪型**（情绪强度/代入感/评论概率/表现力）、**梗型**（记忆点/模仿传播/标题空间/开头吸引力）

## D-021 Token 策略：不压缩换准确率，精细模式预算 5 万 → 8 万（v0.3.1，2026-09-09）

**背景**：51 分钟稿实测成本仅 ¥0.09（4.4 万输入 token）。用户明确：**用户真正付费的是准确率，不是节省几分钱**。

**决策**：不再为省钱压缩 token。精细模式预算由 50000 提到 80000（51 分钟稿不降级、每区块 3 候选）；快速/标准模式预算不变（本来就是低成本选项）。预算估算已计入质检与重扫的开销。

## D-022 评分模型 v3：运营视角五维 + 本地加权定级（v0.3.2，2026-09-09，修订 D-012/D-020）

**背景**：v0.3.1 真实复测出 7 个 A 级，人工复盘发现 AI 仍在当「直播总结助手」——饮料粉洒出来、发现军粮份量少这类「事故型」片段被打高分，部分 B 级反而更有短视频潜质（有误会/反差/记忆点）。v2 权重里没有「三秒吸引力」「反差」这类**传播结构**维度，全是内容维度，AI 只能靠「事大不大、情绪强不强」打分。

**决策**（评分模型 v3，替换 v2 六维）：
- 五维权重：**三秒吸引力 30 / 反差意外 25 / 人物表现力 20 / 独立成片 15 / 事件完整度 10**（config.SCORE_V3_WEIGHTS）
- 判断总纲写进提示词：**「一个不了解主播的新用户刷到这个片段，为什么会停下来？」**
- **复审 AI 只输出五个子分（1-10），不再输出 final_score/grade**；总分由本地按权重加权算出、等级由本地按分数线定——定级可解释、可审计，杜绝 AI「先给个漂亮理由、再顺手打个 9 分」
- 典型案例 few-shot 校准判断（写进复审提示词）：黄腐鸡误当咖啡（误会+反差）＝高价值；军粮「像纸盒子」/罐头「像指甲盖」（具体比喻＝天然标题与记忆点）＝高价值；饮料粉洒出来（纯事故）/"哇好少"（单纯惊讶）＝低价值

**与 D-012/D-020 关系**：修订而非推翻——传播价值导向没变，变的是「用什么维度衡量传播」：内容维度（情绪/争议）降权或删除，换成能直接解释「陌生人为什么停留」的维度。

## D-023 「不值得剪」负面清单：命中即本地封顶 B 级（v0.3.2，2026-09-09）

**背景**：负面规则写进提示词只是「建议」，AI 会选择性无视——「饮料粉洒出来」这类事故仍被捧上 A 级。

**决策**：负面规则升级为**代码层硬约束**：
- 复审时 AI 对每个候选勾选命中的规则（negative_flags，只能从清单选）：**普通失误 / 普通展示 / 单纯惊讶 / 依赖上下文 / 普通评价**
- 本地 `_apply_negative_cap`：命中任一即把该候选封顶为 B 级（config.NEGATIVE_RULE_CAP_GRADE），进不了 S/A；**只降不升**，本来就是 C/D 的候选不受影响
- 清单放 config（NEGATIVE_RULES），要增删规则只改配置不改代码

## D-024 分级体系升为 S/A/B/C/D 五级 + 双理由必答（v0.3.2，2026-09-09，修订 D-018）

**背景**：A 级（≥8）跨度太大——8 分和 9.9 分不是一个量级，爆款苗子被埋在一堆「还不错」里。

**决策**：
- 分级线：**S ≥ 9.0 爆款候选 / A ≥ 8.0 强推荐 / B ≥ 6.0 测试素材 / C ≥ 5.0 备用素材 / D 淘汰**（S 级不设数量上限，宁缺勿滥交给分数线本身）
- 数量模式重定义：自动精选 = 只出 S/A（AI 盖章值得剪）；候选池 = S/A/B/C 全展示；自定义数量 = 按终审分数取前 N 并标注质量名
- 复审每个候选**必答两个问题**：`why_cut`（为什么值得剪 = 陌生人为何停留 + 核心传播点，写不出来说明可能不值得剪）与 `risk`（最大风险/短板，**禁止写「无」**）——逼 AI 对推荐负责，也给用户审计抓手
- D 级淘汰理由由本地组装（risk 或命中规则），不让 AI 写套话

## D-025 v0.4 核心方向：从「找片段」升级为「理解事件」（2026-09-09）

**背景**：v0.3 已解决「找得到」的问题（时间轴 100% 覆盖 + 召回优先 + 质检重扫）。人工复盘暴露出五个新瓶颈，全部集中在一件事上——**AI 在评价一句话，而剪辑师在评价一件事**：
1. 排序和推荐不符合人工判断
2. 一个完整事件被拆成多个碎片（打开包装 / 发现份量少 / 吐槽像纸盒 → 三个低价值候选）
3. 上下文太短，AI 看不到前因后果，单看普通、放在故事里很有价值
4. S/A/B/C 等级表达不了剪辑价值
5. 固定时长限制（提示词里写死「30 秒 ~ 3 分钟」）不符合真实剪辑逻辑

**决策**：v0.4 不增加大量新功能，只做一件事——**让 AI 从寻找片段，升级为理解完整事件并判断传播价值**。五条主线：
- **事件聚合层**：候选 → 合并成事件 → 评价事件（新增 event_id / event_summary / event_steps / main_hook / candidate_clips）
- **上下文窗口**：候选分析时带 ±60 秒上下文，AI 判断是连续事件时自动扩到 ±3 分钟甚至整个事件长度（取代现在的 600 字符上限）
- **动态时长**：取消固定切片长度，AI 输出 recommended_duration（10 秒 ~ 5 分钟）+ duration_reason（为什么不短切/为什么必须保留完整）
- **100 分制评分 + 四档**：开头吸引力 25 / 故事完整度 25 / 人物表现力 20 / 反差意外 20 / 独立观看 10；强推荐 85+ / 推荐测试 70-85 / 素材库 50-70 / 不推荐 <50
- **事件重复合并**：时间重叠 > 50% 且主题相同 → 自动合并成一个事件

**与旧决策的关系**：保留 D-022（AI 只打子分、本地算总分定级，可审计）与 D-023（负面清单本地封顶）——「普通事故 ≠ 爆款」这条铁律不变，只是分级名字从 S/A/B/C/D 换成四档文案。**不推翻，只升级。**

## D-026 事件聚合采用「本地粗合并 + AI 校正」混合方案（2026-09-09，用户拍板）

**背景**：判断「这几个候选是不是同一件事」有三条路，各有代价——纯本地规则零成本但跨区块的同一事件会漏；纯 AI 最准但要吃完稿、成本最高。

**决策**：**混合**——本地先按时间相邻/重叠把候选预合并成「事件簇」（零成本、可控），再让 AI 只针对簇做判断（是否同一事件 + 写出事件摘要和步骤）。
- 好处 1：AI 只看簇不看完稿，输入可控，成本可预估
- 好处 2：跨区块事件（主题相同但时间被切开）由本地时间规则先拉到一起，AI 再做语义判断
- 好处 3：本地规则部分可离线测试，不烧钱

## D-027 人工反馈存 feedback.json（JSON 数组），同 clip_id 覆盖并继承 snapshot（2026-09-09）

**背景**：v0.3 规划里写的是 `feedback.jsonl`（D-010 附近），v0.4 需求文档明确要求 `feedback.json`，且给出记录格式 `{clip_id, user_choice, reason}`。

**决策**（以最新需求为准，修订旧规划）：
- 文件：**feedback.json**，内容是 **JSON 数组**（每条一个反馈对象），而非 JSONL——用户给的格式就是单个对象，数组最直观，也能被任何 JSON 解析器直接读
- 字段：`clip_id` / `user_choice`（喜欢、不喜欢）/ `reason` / `timestamp` + 可选 `snapshot`（片段当时的标题/时间/分数/等级）
- **同一 clip_id 再次反馈 = 覆盖**（用户改主意了，以最新判断为准），不堆积重复数据
- **覆盖时继承旧的 snapshot**：snapshot 是片段的客观信息，不随用户态度改变；用户第二次反馈通常只改态度不带片段信息，不继承的话将来分析「用户喜欢什么样的片段」会缺数据
- 文件写坏 → 自动备份为 feedback.corrupt.json 并重新开始记（不能因为文件坏了就丢掉整个反馈能力）
- **现在不上传服务器、不做分析**（用户明确要求），只攒数据，留给 v0.5/v1.0 训练自己的判断体系

## D-028 词库纠错 v0.4 基础版：纯字符串替换，存稿前纠错（2026-09-09）

**背景**：ASR 不认识主播名、游戏名、品牌、热词——「伏特加」听成「福岛」，主播名写成同音字。输入脏，AI 判断的上限就被压住了（这也是 P1 纠错提前的原因，D-014）。

**决策**（用户明确要求「先做基础版本，暂不做复杂 AI 纠错」）：
- 词库文件 **custom_dictionary.json**，按分类组织（主播名字 / 游戏名称 / 品牌 / 网络热词 / 其他），方便将来做网页词库管理页；程序内部摊平成一张 `{错词: 正确词}` 表
- **纯字符串替换**，零成本、零延迟、结果完全可预测（改了什么一眼能看到）
- **长词优先**：先替换长的错词再替换短的，否则「伏特加酒」会被「伏特加」先咬掉一半
- **纠错时机：ASR 出来之后、存文字稿之前**（`pipeline.apply_dictionary`）——transcripts/ 里的稿子一开始就是干净的；历史稿子用 `pipeline.correct_existing_transcript` 单独跑
- **只改台词，时间戳一个字不动**：按行拆成「[时间戳] 台词」，只对台词部分替换（已写入自测验收项）
- 以 `_` 开头的键是给人看的注释，不会被当成词条

**与 P1 完整纠错的关系**：这一步只是「基础版」。真正的上下文感知纠错（比如根据前后文判断「福岛」到底是地名还是伏特加）留给 v0.4 后续或 v0.5，届时不动本模块接口，只增强替换策略。

## D-029 事件聚合层：本地 soft-signal 粗聚类 + AI 语义判断，先聚合再评分（2026-09-09）

**背景**：v0.3 把「一句话」当高光基本单位，一个完整事件（拆包装→份量少→试吃→吐槽）被拆成 5 个各自低价值的候选。v0.4 核心目标就是「让 AI 理解完整事件」。

**决策**：
- 新增 **analysis/event_cluster.py**（本地粗聚类）+ **AI 事件判断**（Event Judge）两层，插在海选/质检之后、复审之前（**先聚合，再评分**，需求第七条）
- 本地层用 soft signals 给候选两两打「关联分」（时间距离 0.30 + 时间重叠 0.25 + 主题相似 0.30 + 相邻加分 0.15），分数 ≥ 阈值就连边，**连通分量成簇**——链式连接是关键，一个持续 10 分钟的事件只要中间候选连续就能一路串起来
- **所有信号都是连续函数，没有任何「超过 X 秒就断开」的硬规则**（需求原文铁律）
- AI 层（Event Judge）才做最终判断：一簇候选是不是同一件事，并给出事件边界 / 摘要 / 结构（setup/development/payoff）/ 最强爆点 / 置信度

## D-030 本地规则绝不删候选：孤立候选自成一簇（2026-09-09）

**决策**：本地粗聚类只做「提出分组」，**每个候选必须且只能出现在一个簇里**——哪怕它跟谁都不像，也自成一簇（簇内只有它自己），交给 AI 那边判断。本地层不会因为时间距离、关键词不同而丢弃任何候选。这是防止「聚类把候选聚没了」的保险丝，也是全时间轴覆盖（需求测试 9）的前提。

## D-031 事件判断的自适应上下文：先小窗口，故事不完整再扩大（2026-09-09）

**决策**：不给所有事件固定读 ±5 分钟（那样成本爆炸），采用**自适应**策略：
- 第一轮：簇范围往前/后各 90 秒（char_limit 4000）
- AI 若回 `need_more_context=true`（setup/payoff 落在窗口外）→ 扩大到前/后各 240 秒重判一次（最多 1 轮，控成本）
- 上下文来源用 `event_cluster.build_cluster_context`，按簇时间范围捞原文（带时间戳，与文字稿同格式）

## D-032 事件级去重：时间重叠>50% 且主题相同才合并（2026-09-09）

**决策**：v0.3.1 的 exact start/end 去重不够。事件级用「event identity」去重（需求第六条）：两个事件**时间范围重叠超过短边 50%** 且**主题相似度 >0.5**（摘要/标题二元组重叠系数）才视为同一事件合并；合并时取时间并集、source_candidates 累加、摘要取更长、结构缺哪块补哪块。**阈值偏严是故意的**——去重是安全阀，宁可漏合并（留重复），也不要误合并（把两件不同的事并成一件）。

## D-033 clip_id 提前生成并改为 event_id（2026-09-09）

**决策**：v0.3 里 clip_id 只在 `_select_quantity` 最后才发。事件化后，事件在聚合层就生成 `event_id`（ev-001 格式），且 **clip_id 与 event_id 一致**——这样 feedback.json 里记的 id 与原始候选的审计链对得上（需求九「开发者模式可审计」）。`_select_quantity` 不再覆盖已有 clip_id，只对漏发的补发。

## D-034 复审提示词补 event_id 字段 + 五维子分双键名兼容（2026-09-09，修两个潜伏 bug）

**背景**：步骤 2 自测 + 真实 API 测试暴露两个潜伏问题：
1. 复审提示词的 JSON 格式没有 `event_id` 字段，但主流程合并靠它按 id 对号入座——AI 漏条/乱序时顺序兜底会错位
2. 复审提示词让 AI 回 `hook_score`/`contrast_score`…，但 `_parse_review_reply` 用 `item.get("hook")` 取值，真实 API 下全部维度回落默认 5 分（v0.3.2 的假客户端恰好回 `hook` 键，所以离线测试一直没暴露，真实 API 从未测过五维子分）

**决策**：
- 复审提示词 results 条目**增加 event_id 字段**，要求 AI 从候选清单「事件 N（ev-xxx）」原样复制
- `_parse_review_reply` 解析五维子分时**两种键名都认**（先 `hook` 再 `hook_score`），兼容旧假客户端与真实提示词

## D-035 事件拆分时用候选自己的边界，不用整簇判断的边界（2026-09-09，修去重误合并）

**背景**：步骤 2 自测抓出真 bug——AI 判定「这几个候选不是同一件事」要拆开时，`_make_event` 仍用同一个 judge 的 event_start/end/summary 给每个拆分出的单候选事件，导致拆出来的多个事件边界/摘要完全相同，随后被 `_dedupe_events` 误合并回一个。

**决策**：`_make_event` 的 `split` 分支改为**用候选自己的时间边界和标题**，summary/structure/strongest_moment 置空（这些需要 AI 重新判断，拆分后没有）。judge_same_event 仍保留 False、split_by_ai=True，审计链不丢。

## D-036 v0.4 步骤 3：评分升级为 100 分制 + 四档对外（2026-09-09）

**背景**：v0.3.2 用 1-10 小数 + S/A/B/C/D 五级，用户反馈「ABC/S 等级体系不能准确表达剪辑价值」，且 1-10 分太粗、区分度不足。

**决策**：
- 复审 AI **仍只打五维子分（1-10）**，不自由发挥总分——本地按 config.SCORE_V3_WEIGHTS 加权后 **×10 得 0-100 整数总分**（可解释、可审计，杜绝 AI「先给理由再顺手打高分」）。
- 对外四档：**S≥90（必剪）/ A≥80（强烈推荐）/ B≥60（值得测试）/ C≥50（备用/不推荐）**；**D<50 仅作内部淘汰标记**，不再对外展示（C 即最低对外档）。数量模式保留「自动精选（S/A）/候选池（S/A/B/C）/自定义数量」。
- 100 分制阈值 = 原 1-10 制阈值 ×10，语义同构，改动最小且 step1/step2 测试不回退。

## D-037 复审从「一次调用审完所有事件」改成分批 + 全局排序（2026-09-09）

**背景**：事件聚合后单事件原文变长，一次把几十个事件交给 AI 复审会导致单次 prompt 过大、后面的事件被忽略、前半段事件占便宜（前半段偏置）、预算难控、失败难重试。

**决策**：
- 新增 `_review_in_batches`：按 `REVIEW_BATCH.max_events_per_batch`（默认 3）切成若干 batch，**每个 batch 独立一次 AI 复审**；结果**按 event_id 对号入座**（禁止依赖返回顺序）；AI 说某事件上下文不够（context_incomplete）→ 单独用更大窗口重审一次（最多 1 层深扩，控成本）。
- 各 batch 用**同一评分标准**（同一 config 权重 + 同一本地定级引擎），批次间无任何优劣排序。
- 复审完成后 **Global Ranking**：全量按 final_score 降序排一次（跨 batch 统一）。天然消除前半段偏置（排序只看分数不看位置）。
- 整场 AI 复盘报告从复审里**拆出来单独一次小调用**（`_build_ai_report`，独立 REPORT_SYSTEM，基于事件精华卡）——分批的每个 batch 不再背负整场报告，输出体积可控。

## D-038 上下文窗口与剪辑时长完全分离 + 自适应扩窗（2026-09-09）

**决策**：
- **Context Window（AI 阅读范围）≠ Clip Duration（最终剪辑长度）**，二者是独立概念、绝不互相污染。AI 可能读事件前后几分钟，但只剪最能讲清故事的几十秒。
- 复审上下文以**事件边界为锚**：默认事件 start 前/end 后各 **±60s**（config.REVIEW_CONTEXT），需要更多铺垫时依次扩到 **±180s → ±300s**（expand_levels）。**以事件边界为锚整段捞取**，长事件天然完整进入，不会被 ±60s 窗口切掉本体（step2 已聚合的长事件不会被评分阶段重新拆碎）。
- 上下文受字符预算约束（char_budget），超了从最贴近事件中心的部分优先保留，宁缺前后铺垫不切事件本体。
- **动态剪辑时长**：复审 AI 输出 `recommended_start/end + recommended_duration + duration_reason`，长度不设限（一句话梗 8~15s、完整反转 ~40s、连续事件 1~3 分钟甚至更长），不因统一长度强行截断。

## D-039 recommended 时间格式规范化 + schema 校验不静默填 5（2026-09-09）

**背景**：真实 API 实测发现 AI 回 recommended 时间会混用 `HH:MM:SS`（00:48:20）与 `MM:SS`（05:17）；且有的复审结果缺 recommended_start/end/duration。D-034 修的「字段键名不一致导致评分静默回落 5 分」需要一套系统级 schema 校验兜底。

**决策**：
- 复审解析（`_parse_review_reply`）对每个事件做 **schema 校验**：缺 event_id 跳过并 warning；缺五维子分 / recommended_start/end/duration → **记录 warning + 明确 fallback**（子分按 5、剪辑范围按事件边界/时长差兜底），**绝不无提示静默用 5 分掩盖**（需求第十节）。warnings 会打印到日志，让用户知道哪些字段被兜底。
- `recommended_*` 时间在 merge 时经 `_norm_rec_ts` 规范化：HH:MM:SS 统一成 MM:SS（>1h 用 h:mm:ss），非法时间回退事件边界，越界钳回 [0, 时长]。
- 兼容 AI 输出的三种评分键写法：嵌套 `scores:{hook...}` / 平铺 `hook` / 平铺 `hook_score`，`personality` 视为 `persona` 别名（prompt 协议用 personality，内部键保持 persona，避免全链路键名漂移）。

## D-040 v0.4 步骤 3 真实 API 发现的已知风险（记录，不阻塞本步验收）

**记录**：51 分钟真实稿标准模式跑出 18 候选 → 10 事件（degrade_level 3：超「标准」预算，每区块最多 1 候选，候选稀疏）。复审把「2014 罐头事件」的相关候选拆成 ev-006/007/008 三个独立碎片（split_by_ai=True），各自被判 D 级低分淘汰——而 step2 那次（候选更完整）同事件被合并成 2.6 分钟完整高光。

**定性**：这不是步骤 3 的评分/分批/动态时长回归（复审看到的是三个孤立碎片，按碎片本身评低分是合理的）；根因在**步骤 2 事件聚合在稀疏候选下的不稳定性**——degrade 到每区块 1 候选后，同一长事件的候选被拉得太开、本地聚类没链上、AI 也判成不同事件。step2 的 21/21 离线回归证明聚合逻辑本身稳定，但真实场景的候选密度会影响聚合质量。

**待办（不阻塞本步）**：列入步骤 4 或聚合专项优化候选——跨区块同一事件在候选稀疏时的再合并；degrade_level 2/3 时对质检疑似漏检区的罐头类多候选做更宽容的聚类。

## D-041 「内容评分/评级」与「推荐剪辑」解耦 + 自动精选改 A 优先/B 补位（V0.4.2，2026-09-11）

**背景**：51 分钟真实稿（V0.4.1，精细模式）跑出 13 个事件：8 个 B、5 个 C、1 个 D，**最高分 79.5（B）**。旧逻辑「自动精选 = 只取 grade in (S,A)」→ **最终 0 条高光**。人工复盘认为这批内容里有真爆点（微波炉炸了、过期罐头、咖啡鞠躬道歉），0 输出是产品逻辑问题，不是内容问题。

**定性（用户三问的答案）**：
1. **两者兼有，产品逻辑为主**：代码按设计执行，无 bug；但把「内容质量分级」直接当成「推荐名单」是设计缺陷（耦合）。
2. **是的，被错误绑定**：`picked = [c for c in candidates if c["grade"] in ("S","A")]`，以及 `ai_recommend = grade in ("S","A")`，都是同一处绑定。
3. **Auto 在 A 不足时应该从高质量 B 补充**。
4. **C 不无条件自动推荐；D 永不自动推荐**。
5. **不修改底层评分体系**——评分只做它该做的事：描述内容质量。

**决策**：
- **职责分离**：
  - `grade` / `score`（评级/评分）——只描述**内容质量**，由复审五维加权本地定级（D-022 不变）。
  - `recommended` / `recommend_tier`（推荐剪辑）——**产品层筛选结果**，由新增的 `_pick_recommendations()` 统一决定，与 grade 解耦。
- **自动精选策略（A 优先 → B 补位 → C 兜底）**：
  1. 先取全部 S/A，按分数降序，**上限 `AUTO_SELECT_TARGET`（默认 8）**；
  2. 不满目标数 → 用 B 级里 `final_score >= AUTO_B_FILL_MIN_SCORE`（默认 60，即 B 线）的按分补位；
  3. 连一个 S/A/B 都没有 → 兜底最多 `AUTO_C_FALLBACK_MAX`（默认 3）个最佳 C，标 `C_fallback`。
  **目标数量是上限而非配额**（宁缺毋滥，不硬凑），**D 级永不进入推荐**。
- **数量模式语义**（保持不变，只是推荐标记独立）：自动精选=只展示推荐名单；候选池=展示 S/A/B/C 全部（推荐名单是其中子集）；自定义数量=按分数取前 N，入选即推荐。
- **解耦的可见后果**（有意为之）：*A 级内容也可能因推荐名额已满而落选*——落选条目的 `reject_reason` 会写明「X 级内容，但推荐数量已达目标（N 条）」。这正是「评分高 ≠ 一定进推荐名单」的体现。
- `ai_recommend` **保留原义**（= S/A 内容级 AI 背书），不改变语义，避免旧读者/旧数据被误解释。

## D-045 Chapter/Story 必须由主流程按当前视频现算，禁止任何固定样例 fallback（V0.4.4，2026-09-11）

**背景（严重数据绑定 bug，用户实测发现）**：用任意新视频分析时，「推荐剪辑」正确（来自本次分析），但 UI 的「直播内容结构」**永远显示同一套 Chapter 01/02/03/04**——即开发阶段那次 51 分钟测试视频的 PoC 结果。换视频、重跑都不变。

**根因**：Chapter/Story 分层**从未接进主流程**。它只在 PoC 阶段（`poc/v04_pipeline.py`）对一场 51 分钟测试视频跑过一次，产物写死为 `poc/story_segmentation_result.json`；而主流程第 8 层的 `story_context.load_structure()` **无条件读这个固定文件**，且 `load_story_groups()` 在 `source=None` 时也回落到它。于是：
- 结构 = 那场 51 分钟视频的（恒定）；
- 推荐剪辑 = 本次视频的；
- 两者**不同源**，且结构对所有视频恒定。

**决策**：
1. **禁止任何固定样例默认**：`story_context.load_structure(source=None)` 返回**空结构**；`load_story_groups(source=None)` 返回 **{}**。文件路径只在被**显式**传入时才读（`source` 支持 dict / 路径 / None）。绝不隐式加载固定文件，绝不静默 fallback 到另一场视频的结构。
2. **Chapter/Story 进主流程现算**：新增 `analysis/chapter_story.py`。在事件层产出之后、返回结果之前，用**本视频的事件列表**调 AI 切 Chapter，再在每 Chapter 内切 Story。失败降级：Chapter 失败 → 跳过该层；Story 失败 → 该 Chapter 单 Story（不阻断主结果）。
3. **结构按视频缓存隔离**：缓存写到 `structures/<文字稿文件名>.json`（`config.STORY_CONTEXT.cache_dir`，默认 `structures`）。读取时**必须**文件名与时长都一致才复用；不匹配/不存在 → 返回 None（本次现算）。**缓存只是省钱的加速器，不是数据来源**——它永远只对应这一份稿子。
4. **删除固定路径配置**：`config.STORY_CONTEXT` 移除 `"story_file"`（那正是 bug 源），新增 `"cache_dir"`；新增 `CHAPTER_STORY`（enabled / max_chapters / 输出 token 上限）。
5. **开发夹具隔离**：`poc/story_segmentation_result.json`、`poc/ai_chapter_result.json` 移入 `poc/fixtures/`；PoC 脚本与测试显式传路径，杜绝被生产代码路径误读。
6. **聚合阶段的 Story 先验也改为读本视频缓存**（`_run_event_aggregation(transcript_path=...)`），不再读全局固定文件。

**数据流（修复后，唯一正确路径）**：
```
文字稿 → 事件发现/聚类/判断 → 事件列表
  → chapter_story.get_or_build_structure(client, transcript_path, events, duration)
  → 先查 structures/<本稿名>.json（同名同时长才用，source=cache）
  → 否则用本稿事件现算 Chapter → Story（source=fresh）并写入该视频自己的缓存
  → 挂事件 + 派生 Story 评分 → 结果 structure → UI「直播内容结构」
（始终与本次 highlights 出自同一次分析、同一批 event_id）
```

**影响面**：新增 `analysis/chapter_story.py`、`test_v040_step7.py`、`verify_v044_two_videos.py`；改 `analysis/story_context.py`、`analysis/__init__.py`、`config.py`、`analysis/prompt_builder.py`（CHAPTER_SYSTEM/STORY_SYSTEM + 两个 build_*_prompt）、`ui.py`（降级文案去掉固定文件引用）、PoC/测试路径。**未改动**：Event 层、聚类、评分体系、推荐筛选（D-041）、软边界原则（D-025/D-026）、Chapter/Story 提示词方法论（沿用已验证版本）。

**验证**：test_v040_step7.py 20/20（两视频结构各自对应 / 连续运行不继承 / 推荐与结构同源 / 缓存隔离 / 无 fallback / step1~6 全量回归）；test_ui_selftest.py 15/15；真实双视频验证见 `v044_two_videos_report.txt`。

## D-046 本地 ASR 失败必须分层可辨；模型一律离线优先加载（V0.4.5，2026-09-11）

**背景（严重问题，用户实测）**：网页版「上传新视频识别」对**任何**视频都统一提示「视频处理失败，请换一个文件试试」——正常视频、损坏视频、无音轨视频全都一样，且开发者模式下也看不到真实原因。

**根因（两层，缺一不可）**：
1. **正常视频也失败的真因**：`faster_whisper.WhisperModel()` 加载模型时会经 `huggingface_hub` 做一次**远程校验**，即使模型文件已在本地缓存也要联网。本机网络经代理（`http_proxy=127.0.0.1:4492`）访问 HuggingFace 返回 **502 Bad Gateway** → 抛 `httpx.ProxyError` → 被 `ui.py` 的 `except Exception` 统一吞掉。**现象像"视频坏了"，其实视频完全正常。**
2. **无法区分的真因**：`pipeline.extract_audio()` / `process_video()` 失败只 `return None`，信息在返回时就被丢掉；UI 拿到 None 只能给一句通用提示。于是「损坏 / 没音轨 / 模型没装 / 提取失败 / 推理失败」全部塌缩成同一句话，原始异常与 traceback 都不可见。

**决策**：
1. **新增 `errors.py`**：全项目统一的 `ProcessError(stage, message, detail)` + stage 常量（`media_unreadable` / `no_audio_track` / `audio_extract` / `ffmpeg_missing` / `dependency` / `model_missing` / `model_load` / `asr_inference` / `asr_empty` / `unknown`）。`detail` 存原始错误与 ffmpeg stderr 尾巴，供开发者视图。
2. **流水线显式分层检查**（**不改阶段划分**）：
   - `check_video_readable()` —— 存在 / 非目录 / 非空（0 字节）
   - `probe_media()` —— 用 `ffmpeg -i` 探测（**不额外引入 ffprobe**）：是否可读、有没有 `Audio:` 流、时长；关键字表判定损坏
   - 不可读 → `media_unreadable`；可读但无音轨 → `no_audio_track`；提取失败 → `audio_extract`
   - `extract_audio()` / `process_video()` **失败改为抛 ProcessError，不再返回 None**
3. **模型加载改离线优先（核心修复）**：`LocalWhisperRecognizer._load_model()` 先 `local_files_only=True` **完全离线**从本地缓存加载；只有缓存里确实没有该模型时才联网下载（首次安装路径保留）。两类失败分别抛 `model_missing` / `model_load`。
4. **识别器缓存只缓存成功结果**：加载失败不留半成品，用户装好模型后不必重启网页版。
5. **异常不再被吞**：`asr/local_whisper.py` 的 `ImportError` 与 `raise SystemExit(1)` 改为抛 `ProcessError(dependency)`；`transcribe()` 用 try 包住**整个惰性生成器循环**（faster-whisper 真正推理发生在迭代里），失败抛 `asr_inference`。
6. **UI 按 stage 分别提示**：`ui.py._ASR_ERROR_UI` 十条文案（标题 + 该怎么做）；`except BaseException` 兜底成 `unknown`；**完整 traceback + 原始 detail + 控制台输出**放进「🔧 开发者」折叠区——**不吞底层异常**。

**未改动**：ASR 架构与阶段划分、Chapter/Story/Event/Highlight/Recommendation、评分体系。`main.py` 只把「判 None」改成 try/except（行为等价、信息更全）。

**影响面**：新增 `errors.py`、`test_v045_asr_errors.py`；改 `pipeline.py`、`asr/local_whisper.py`、`asr/__init__.py`、`ui.py`、`main.py`、`.gitignore`。

**验证**：test_v045_asr_errors.py **18/18**（7 种情况 stage 互不相同，界面文案互不重复且旧统一提示已移除）；真实 6 分钟视频 **41 句 / 85s** 成功走完本地 ASR（模型「离线加载」）；UI 自测 15/15；step1~6 回归全过。

## D-048 ASR 必须走 Provider 抽象，业务层不许直接依赖 faster-whisper（V0.5，2026-09-11）

**背景**：用户明确要求「Chapter / Story / Event / Highlight 不应该直接依赖 faster-whisper」，未来要能接云端 ASR。迁移审查确认：`pipeline.get_recognizer()` 把 faster-whisper 写死在主流程里，`ui.py` 直接 `import asr`，业务层拿不到「换引擎」的机会。

**决策**：
1. 新增 `asr/provider.py`：`AsrProvider` 约定（`id / name / kind / is_available() / prepare() / release() / transcribe(audio_path)`），能力边界**只有一条**：「音频文件 → [Segment]」。Provider **不碰** Chapter/Story/Event/Highlight/评分/推荐。
   - `FasterWhisperProvider`（本期真正实现；`model_path` 给了就直接用该目录 → **完全离线**，否则退回 `model_size` + HF 缓存，兼容网页版/命令行老路径）
   - `CloudAsrProvider` / `TwoPassProvider`：**只预留接口**，不接具体服务，`transcribe()` 抛带 stage 的 `ProcessError`

4. 所有 ASR 失败一律抛 `errors.ProcessError`（沿用 D-046 的 stage 语义），**不用新一套错误类型**。

**边界**：现有 `pipeline.process_video()` 的流程与 `asr.create_recognizer()` 老入口**都保留**（网页版与命令行行为不变）；Provider 是**新增的一条路**，不是替换。

## D-049 模型不随安装包分发；用 Model Registry 统一管理下载与校验（V0.5，2026-09-11）

**背景**：faster-whisper small 的 `model.bin` 就有 ~464 MB。塞进安装包会让「下载一个 Setup.exe」变成下载几个 GB，而且用户可能想换 tiny/medium。

**决策**：
1. **安装包不含任何模型**。首次运行时检测；缺失则界面引导「一键安装」（进度 / 失败提示 / 可重试 / 断点续传 / 完整性校验）。
2. 新增 **`models_registry.json`（Model Registry / Manifest）**：每个模型一条，字段 = `id / kind / engine / name / description / recommended / default / size_hint / repo_id / revision（版本）/ base_url（下载地址）/ files / primary_file / min_primary_bytes（大小下限校验）/ sha256（清单写死的校验值，可留空）`。
   - 下载地址、文件清单、校验规则**集中在这一个文件里**，不散落在业务代码
   - 支持**工作区覆盖**（用户数据目录放了同名清单就用它）→ 日后可热更新清单，不用重装程序
3. 新增 `desktop/services/model_manager.py`（`ModelManager`）：`list_status()` / `resolve_local()`（工作区优先 → 回退本机 HuggingFace 缓存）/ `install()`（流式下载 + `.part` 断点续传 + 写盘失败分类型报错）/ `verify(deep=True)`（文件齐全 + 主文件大小下限 + sha256）/ `adopt_from_hf_cache()`（**用户以前跑过网页版，模型已在缓存里 → 直接登记，不重复下载**）/ `copy_into_workspace()`（离线兜底：用户手动指定文件夹）/ `remove()`（**只删工作区副本，绝不动 HF 缓存和用户原文件夹**）。
4. 模型错误沿用 `ProcessError` 的 `model_missing` / `model_load` 两个 stage，界面据此分别给出「去安装」/「去校验」的动作按钮。

**边界**：`model_manager` **不认识** faster-whisper（引擎细节留给 D-048 的 Provider）；**不自动删**用户任何已有文件。

 长任务必须上报「真实进度」，不许用定时器编假百分比（V0.5.2，2026-09-12）

**背景**：本地识别一场 51 分钟直播要十几分钟。这段时间界面上只有一个转圈的不定进度条和一句
"语音识别"，用户完全无法判断程序在跑还是卡死了 —— "以为软件死了"的直接来源。

**决策**：
1. 建立**统一的进度事件协议**（`stages.py`）：`{stage, title, percent, detail, index, total_steps}`。
   六个阶段：读取视频 / 提取音频 / VAD 人声检测 / 语音识别 / AI 分析 / 生成结果。
2. **百分比必须是真实算出来的**：
   - 语音识别 = 已处理音频时间 / 视频总时长（faster-whisper 每句话都带音频里的结束时间）
   - AI 分析 = 已扫描区块数 / 总区块数（解析分析过程的日志得到，如 `[海选] 区块 3/12`）
   - **算不出进度的阶段（VAD、音频提取）percent 就是 None**，界面显示"进行中"而不是编一个数字
3. `ProgressSink` 负责三件事：**节流**（同阶段 0.15s / 0.5% 内的变化丢掉，否则每秒几十条会淹掉主线程）、
   **兼容旧回调**（只吃一个字符串的函数自动降级）、**绝不抛错**（进度上报失败不能连累主流程）。
4. **AI 阶段的进度不改 analysis/ 一行代码**：用 `_LineTee` 流式捕获分析过程的 print，
   在 `desktop/services/ai_progress.py` 里把日志行翻译成进度。

**验收**：测试会逐条核对每个进度事件的 `percent` 与它 `detail` 里"已处理 / 总时长"的比值，
误差 > 1% 即判失败 —— 从机制上杜绝"假进度条"回潮。

## D-051 安装/卸载/启动都不能阻塞主线程；失败必须留日志（V0.5.2，2026-09-12）

**背景**：用户报「第一次安装偶尔卡死，等一会儿能装完」。定位到三处主线程重活，以及卸载的三个真因
（见 CHANGELOG v0.5.2）。共同点是：**耗时操作放在主线程 + 失败被静默吞掉**。

**决策**：
1. **安装器**：解压载荷、统计目录大小、建快捷方式全部在后台线程；主线程只每 60ms 轮询队列刷新界面。
   安装逻辑抽成模块级 `run_install()`，界面模式与 `--silent` 静默模式共用同一条代码路径。
2. **启动**：界面**先显示出来**，环境自检在后台跑；项目列表异步加载
   （并要有"作废在途异步结果"的机制，否则旧数据会覆盖新刷新）。
3. **卸载器**：先复制自己到 `%TEMP%` 再执行 —— 自己不在被删目录里，才能把安装目录删干净。
   删除失败不许吞掉：
   - 带重试（`_rmtree_retry`）
   - 还删不掉则**交给系统后台继续删**（`_schedule_late_cleanup`）
   - **注册表一定清理**，保证「应用和功能」不残留（哪怕文件有残留）
   - "程序还在运行"从**中止卸载**改为**警告但继续**（中止会让用户以为卸载没反应）
4. **日志**：安装（`%TEMP%\AILiveClipper_setup.log`，装完复制进安装目录）、
   启动（`logs/desktop_startup.log`，含各阶段耗时）、卸载（`%TEMP%\AILiveClipper_uninstall.log`）——
   一律落文件，因为打包后的窗口程序没有控制台。

**踩坑固化**：用 `DETACHED_PROCESS` 启动 `cmd.exe` 时命令**不会执行**（cmd 需要控制台），
后台清理会静默失效 → 这类"辅助进程"统一用带 BOM 的 PowerShell 脚本 + `CREATE_NO_WINDOW`。

**验收**：`packaging/test_install_uninstall.py` 逐个断言安装目录 / 注册表项 / 桌面与开始菜单快捷方式
真的消失；删不掉不算过。
