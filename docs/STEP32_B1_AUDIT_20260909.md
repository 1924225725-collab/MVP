# Step 3.2-B1 审计：海选候选单位「爆点句 → 事件种子」

日期：2026-09-09 ｜ 状态：纯分析，未改代码 ｜ 前置：A1/A2/A3 已冻结验证

---

## 1. 现状证据（A3 真实结果，精细 degrade0，39 候选 → 17 事件）

| 事实 | 数据 |
|---|---|
| 单候选事件 | **11/17**（事件没聚合过，等于海选报啥就是啥） |
| 其中 ≤28s 的短碎片 | **6 个**（ev-013 3s、ev-012 5s、ev-007 12s、ev-010 14s、ev-009 19s、ev-015 28s） |
| ≤54s 的单候选 | 再 +3（ev-005 40s、ev-003 54s、ev-008 54s×2候选） |
| 聚合成功的事件 | 全部 ≥64s（ev-017 96s A 级、ev-014 299s、ev-016 168s、ev-006 144s、ev-002 139s、ev-004 111s） |
| 长事件怎么来的 | 罐头 299s = **6 个候选碎片拼**（海选把完整事件拆了报，聚合层碰运气拼回） |

**规律**：海选报的候选本身就以 10~30 秒的「爆点句」为主；能成为长高光的，都是聚合层把碎片拼成功的幸运儿。拼不上的（11 个孤立单候选）就是用户看到的碎片。

## 2. 根因（代码级）

**海选模板 `_SCREENING_TEMPLATE` 从未定义「候选应该是一个多长的完整事件单元」。**

具体四处引导都在推「报短句」：
1. 「每段至少挑出 1 个最有潜力的候选」→ AI 每区块先找最炸的一点，不是一段
2. 「三秒吸引力：标题+开头 3 秒有没有钩子」→ 用「开头 3 秒」的框架，天然对应 10-30s 短视频
3. 「宁多勿少」+ 每区块 max_candidates=3（精细/标准）→ AI 倾向把 3 个名额分给 3 个不同的「点」，而不是 1 个完整事件
4. **候选 JSON 只有 start_time/end_time/title/reason，没有任何「事件边界理由 / 上下文 / 事件摘要」字段**——AI 没有渠道表达「这段其实是前面 X 事件的延续」

→ 候选单位 = 爆点句 → 聚合层拿到的是一堆碎种子 → 拼得上就长，拼不上就 D/C。

## 3. 用户 4 个痛点的对应

| 痛点 | 根因映射 |
|---|---|
| 10~20 秒碎片过多 | 海选报短候选，聚合对孤立短候选无能为力（11/17 单候选） |
| 完整事件召回不足 | 完整事件要等聚合「碰运气」，海选不直接给事件种子 |
| 真正爆笑点容易漏 | 真爆点常是「铺垫→爆发」整体，短候选把铺垫切掉，复审只见孤句 |
| 候选缺事件上下文 | JSON schema 根本没有事件上下文字段 |

## 4. 最小改法（不改架构，只动海选一层）

**核心：让海选直接产出「事件种子」——候选默认是一个完整小事件（30s~3min），短梗作为显式例外；每个候选带事件上下文摘要。**

### 改动 1：海选模板加「候选单位」定义（prompt_builder._SCREENING_TEMPLATE）
在「判断视角」之前插入一段（约 5 行）：
- 候选默认 = **完整事件单元**：从铺垫/开场到结果/反应的一整段（例：拆包→发现份量→试吃→吐槽→反应，这是一整个候选，不是一个）。范围 30 秒~3 分钟，宁可把边界放宽到事件自然起止。
- 一句话短梗（真正独立的金句/反应，不需要铺垫）才允许 10 秒级短候选。
- **同一事件的多个爆点 → 只报一个候选**（范围覆盖整个事件），不要把一件事拆成多个候选。

### 改动 2：候选 JSON 加两个可选字段（模板 + _parse_screening_reply）
```
"event_context": "这个片段前面的必要背景，30字内。例如：主播正在测评军粮，前面已经吐槽了份量少",
"event_boundary_note": "为什么 start/end 选在这：完整事件的起止依据，30字内。例如：从拆包开始到吐槽完为止"
```
- 解析器透传，下游 `_make_event` 不读这两个键 → **零破坏**（已核对消费键清单）
- 事件聚合失败成孤立候选时，复审能靠 event_context 理解它，不再当「没头没尾的孤句」判 D（呼应 A3 门控）

### 改动 3（可选，最小）：海选后候选去重不拆
不改。质检候选去重已由 A1 修好。

## 5. 预期影响

- **海选候选数下降**（每区块可能从 3 个短候选 → 1-2 个事件种子）→ token 略省
- **单候选短碎片减少**：短梗仍是短候选（保真），但「需要铺垫的完整事件」不再被切成碎种子
- **聚合成功率上升**：事件种子天然比爆点句更容易被 AI judge 判定为「同一件事」
- **D 级误杀继续下降**：孤立候选带 event_context，复审有背景可看
- 风险：海选可能把不同的事错误并进一个宽候选 → 靠 step2 AI judge 的 same_event=False 拆分兜底（已有机制）

## 8. 风险与回退
- 主要风险：海选「宽候选」把相邻不同事件包进去 → AI judge 拆（已有机制）+ 复审低分淘汰，风险可控

- 若验收 1/2 不达标 → 回退模板措辞重新校准，不动代码结构
